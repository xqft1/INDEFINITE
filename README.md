# INDEFINITE

## Permanent Uniswap v4 Liquidity Locking

**INDEFINITE** is an immutable Uniswap v4 LP locker for Ethereum.

It allows anyone to permanently lock a Uniswap v4 liquidity position while retaining the ability to claim the trading fees generated by that position.

Once an LP position is locked, the NFT and its underlying liquidity can never be withdrawn through INDEFINITE.

> **Lock forever. Collect fees forever.**

# Why INDEFINITE Exists

Liquidity locks are commonly used by token projects to demonstrate that liquidity cannot simply be withdrawn by the project creator.

INDEFINITE takes this concept to its logical extreme.

There is:

- no unlock date
- no owner-controlled withdrawal
- no emergency liquidity withdrawal
- no rescue mechanism for LP NFTs
- no upgrade mechanism
- no admin capable of releasing liquidity

The liquidity position is intended to remain inside the locker permanently.

At the same time, the original depositor remains entitled to the trading fees generated by their position.

This creates a simple distinction:

```text
LIQUIDITY PRINCIPAL
        |
        v
   LOCKED FOREVER


TRADING FEES
        |
        v
   CLAIMABLE
```

# Trust Through Transparency

INDEFINITE is designed to make liquidity commitments easy to verify on-chain.

Instead of asking users to trust a promise that liquidity will not be removed, anyone can inspect the Ethereum blockchain and confirm that the Uniswap v4 LP NFT is owned by the INDEFINITE contract.

The contract intentionally contains no mechanism that allows the LP NFT to be transferred back out.

This can provide token communities with stronger transparency around long-term liquidity commitments.

Anyone can independently verify:

- which LP NFTs are locked
- who originally deposited each position
- the remaining liquidity in the position
- the contract source code
- the absence of an owner withdrawal function
- the protocol fee rules
- fee claim transactions

# How It Works

Each Uniswap v4 liquidity position is represented by an NFT.

When a user locks a position:

```text
User
 |
 | Uniswap v4 LP NFT
 v
INDEFINITE
 |
 | ownership remains here permanently
 v
Locked Position
```

INDEFINITE records the original depositor:

```solidity
beneficiary[tokenId]
```

That address becomes the permanent fee beneficiary for that position.

The NFT remains owned by INDEFINITE.

---

# What Is Permanently Locked?

When you lock a position, you are locking the entire Uniswap v4 position represented by that NFT.

This includes the position's:

- liquidity
- pool
- token pair
- fee tier
- tick spacing
- hook
- price range
- lower tick
- upper tick

The range cannot later be repositioned through INDEFINITE.

If the market price moves outside the position's range, the position remains locked in that range.

It will generally stop earning normal LP fees while out of range and may begin earning again if the price returns to the range.

Choose your liquidity range carefully before locking.

---

# Trading Continues Normally

Locking an LP NFT does **not** remove its liquidity from the Uniswap pool.

The liquidity remains available to traders.

Users can continue trading against the pool normally.

The position can continue generating fees while the liquidity is active.

INDEFINITE holds ownership of the LP NFT, not the underlying pool itself.

---

# Fee Collection

INDEFINITE allows the original depositor to collect accrued fees without intentionally removing liquidity principal.

For normal positions:

```solidity
claimFees(tokenId)
```

For hooked positions requiring custom hook data:

```solidity
claimFees(tokenId, hookData)
```

Only the recorded beneficiary can initiate a fee claim for that position.

---

# Protocol Fee

INDEFINITE charges a **1% protocol fee on collected LP fees**.

For normal users:

```text
99% -> LP beneficiary
 1% -> INDEFINITE fee recipient
```

The fee recipient is permanently defined as:

```text
0x9a30Cf4527D2CC80884405e16337149ab59e3d6E
```

Positions originally deposited by that address are exempt from the protocol fee.

For those positions:

```text
100% -> beneficiary
```

The 1% fee applies to the **fees being collected**, not to the locked liquidity principal.

# How To Lock A Position

## Method 1: Use `lock()`

First approve INDEFINITE to transfer your Uniswap v4 position NFT.

Then call:

```solidity
lock(tokenId)
```

Example:

```text
lock(123456)
```

The contract transfers the NFT into INDEFINITE and records the caller as the permanent beneficiary.

---

## Method 2: Direct `safeTransferFrom`

Advanced users may directly use ERC721:

```solidity
safeTransferFrom(
    yourAddress,
    indefiniteAddress,
    tokenId
)
```

The locker will record the `from` address as the beneficiary.

---

# IMPORTANT: Do Not Use Plain `transferFrom`

Do **not** directly send a position using:

```solidity
transferFrom(...)
```

Use:

```solidity
lock(...)
```

or:

```solidity
safeTransferFrom(...)
```

The beneficiary is recorded through the ERC721 safe-transfer callback.

A plain `transferFrom` does not execute that callback.

If a position is sent directly using `transferFrom`, the NFT may become permanently trapped inside INDEFINITE **without a registered beneficiary**, meaning its fees may also become inaccessible.

This is one of the most important usage warnings.

---

# Claiming Fees

For a standard position:

```solidity
claimFees(tokenId)
```

For positions requiring hook data:

```solidity
claimFees(tokenId, hookData)
```

The contract:

1. identifies the permanent beneficiary
2. performs the Uniswap v4 fee collection operation
3. receives the collected currencies
4. calculates the protocol fee
5. sends 99% to the beneficiary
6. sends 1% to the protocol fee recipient

The LP NFT remains inside INDEFINITE.

---

# Hooked Positions

Uniswap v4 allows pools to use hooks.

A hook is part of the pool's identity.

A PIZZA/ETH pool with Hook A is therefore different from a PIZZA/ETH pool with Hook B.

Someone cannot simply add a new hook to an existing pool.

INDEFINITE allows `hookData` to be supplied during fee collection so that positions using hooks can interact with their hook where required.

However, this does **not** mean every possible hook is guaranteed to work.

See the risks section below.

---

# Risks

INDEFINITE is intentionally irreversible.

Understand these risks before locking any position.

## 1. Permanent Loss Of LP NFT Control

Once successfully locked, the LP NFT is intended to remain owned by INDEFINITE forever.

There is no:

- withdrawal function
- unlock timestamp
- owner recovery
- admin recovery
- rescue function
- emergency withdrawal
- migration function
- upgrade path

Do not lock a position unless you are prepared to permanently give up control of its principal.

---

## 2. Liquidity Cannot Be Repositioned

Uniswap v4 concentrated liquidity positions use defined price ranges.

After locking, INDEFINITE provides no mechanism to withdraw the liquidity and recreate it at a different range.

If your position becomes badly positioned relative to market price, you cannot rebalance it through this contract.

---

## 3. Out Of Range Positions

If market price moves outside your liquidity range, the position can remain permanently locked while being out of range.

This may dramatically reduce or stop normal LP fee generation until the market price returns to the position's range.

Permanent liquidity does not mean permanently productive liquidity.

---

## 4. Hook Compatibility Is Not Guaranteed

Uniswap v4 hooks can execute custom logic during liquidity operations.

INDEFINITE supports passing arbitrary `hookData` during fee claims.

However, a hook may:

- reject fee collection
- require specific hook data
- impose additional conditions
- deliberately revert
- contain bugs
- change the economics of the pool
- behave unexpectedly
- prevent certain liquidity operations

INDEFINITE cannot override the rules imposed by a pool's hook.

Therefore:

> A position may remain permanently locked even if its hook later makes fee collection impossible.

Users should understand the hook associated with a position before locking it.

---

## 5. Malicious Hooks

A malicious or poorly designed hook may create risks that originate outside INDEFINITE.

Locking a position does not make its hook safe.

Users should independently assess the hook contract used by their pool.

---

## 6. Smart Contract Risk

INDEFINITE is smart contract software.

Smart contracts can contain undiscovered vulnerabilities.

The included tests demonstrate intended behavior, but tests do not prove the absence of all vulnerabilities.

The contract should not be treated as risk-free.

---

## 7. No Recovery From User Error

The absence of an admin recovery mechanism is intentional.

It also means there is nobody who can fix certain mistakes.

Examples include:

- locking the wrong position
- choosing the wrong liquidity range
- locking into the wrong pool
- interacting with an unsafe hook
- sending the NFT using the wrong ERC721 method
- permanently losing access to the beneficiary wallet

There is no administrator who can reverse these actions.

---

## 8. Beneficiary Wallet Loss

The original depositor is permanently recorded as the beneficiary.

If control of that address is lost, there is no function to change the beneficiary.

Keep the beneficiary wallet secure.

---

## 9. Exotic ERC20 Tokens

The contract is primarily designed around conventional ERC20 tokens and native ETH.

Unusual token behavior may cause unexpected results.

Examples include:

- rebasing tokens
- fee-on-transfer tokens
- tokens that block transfers
- tokens with unusual return values
- malicious tokens
- tokens capable of changing balances unexpectedly
- upgradeable tokens whose behavior later changes

Users should assess the assets in their pool before permanently locking a position.

---

## 10. Token Contract Risk

Even if INDEFINITE itself works correctly, one of the assets inside the pool may contain:

- minting vulnerabilities
- blacklists
- transfer restrictions
- admin controls
- upgradeability
- exploits
- malicious behavior

A liquidity locker cannot protect users from the risks of the tokens themselves.

---

## 11. Uniswap Protocol Risk

INDEFINITE relies on Uniswap v4 infrastructure.

Any vulnerability, unexpected behavior, integration issue, or protocol-level problem affecting Uniswap v4 may also affect locked positions.

---

## 12. Permanent Contract Design

INDEFINITE itself cannot be upgraded.

This is a trust-minimizing feature, but also a limitation.

If:

- a better implementation is created
- Uniswap architecture changes
- a bug is discovered
- new functionality becomes desirable

existing locked positions cannot simply be migrated by an administrator.

A new contract would need to be deployed, while existing positions would remain in the original locker.

---

## 13. Fee Claim Failure

The ability to claim fees depends on the underlying position, pool, assets, hook and Uniswap infrastructure functioning correctly.

INDEFINITE is designed to allow fee collection, but it cannot guarantee that every future position will remain claimable forever.

---

## 14. Transaction Costs

Claiming fees requires an Ethereum transaction.

When Ethereum gas prices are high, it may not be economically worthwhile to claim small amounts of fees.

---

## 15. Protocol Fee Rounding

The protocol fee is calculated using integer arithmetic.

Very small fee claims may round the 1% protocol fee down to zero for extremely small token amounts.

This is standard Solidity integer behavior.

---

## 16. Frontend Risk

Users do not need to rely on any particular website or frontend.

The contract can be interacted with directly through Ethereum tools such as Etherscan.

A frontend may:

- go offline
- contain bugs
- display incorrect information
- be compromised

Always verify transaction details before signing.

The Ethereum contract is the source of truth.

---

## 17. Fake Contracts

Because INDEFINITE is permissionless and open source, other contracts may copy its code or branding.

Always verify the contract address.

Official Ethereum deployment:

```text
0x54106486bb295f78f5fEAcd2E7B6d9f6Ba3b6b84
```

Do not rely solely on contract names or website branding.

# Permissionless

INDEFINITE is not limited to a single project.

Anyone with a compatible Ethereum Uniswap v4 position can use the same deployed contract.

Different users can lock completely unrelated positions.

Each `tokenId` has its own permanent beneficiary.

For example:

```text
Position #100
Beneficiary: Alice

Position #200
Beneficiary: Bob

Position #300
Beneficiary: Charlie
```

All three positions can exist inside the same INDEFINITE contract.

---

# No Ownership

INDEFINITE intentionally does not use an administrative ownership system for controlling locked LP positions.

There is no administrator capable of deciding later that a position should be released.

The fee recipient does **not** have custody powers over other users' positions.

The fee recipient simply receives the predefined 1% share of collected fees.

# Security Philosophy

The contract intentionally has a narrow scope.

INDEFINITE is not designed to:

- manage positions
- rebalance liquidity
- migrate liquidity
- withdraw liquidity
- change beneficiaries
- upgrade itself
- rescue LP NFTs

Its purpose is simpler:

```text
ACCEPT LP
    |
    v
LOCK LP FOREVER
    |
    v
ALLOW FEES TO BE CLAIMED
```

Reducing administrative functionality reduces the number of privileged actions users must trust.

It does not eliminate smart contract risk.
